# R1 closeout: explain where reuse is lost

Decision: diagnostic phase complete, subject to the regression/security results
recorded below. Semantic utility and safety remain unproven; this is not Gate A
recovery or a new model evaluation. No historical sealed stream was rerun.

## What changed

Added immutable offline diagnosis export, recorded eligibility snapshots and
semantic decision stages, an authored policy-boundary audit, and strict handling
of missing/malformed diagnostics. No eligibility rule, threshold, matcher
approval, serving default or provider route was relaxed. The new roadmap adopts
phase-closeout commits and the user's delivery window.

## Reproduction

```bash
python scripts/diagnose_reuse.py \
  --pairs data/candidate_b_train_pairs.json \
  --license-note 'Existing exposed development QQP/PAWS pairs; source terms recorded in docs/FACTS.md, no new licensing claim.' \
  --output-dir runs/r1-recompute
python scripts/audit_policy_scope.py
```

Aggregate output, implementation hashes and source/trace binding are in
`R1_REUSE_DIAGNOSIS.json`; source request traces remain under the ignored local
run directory and are regenerated by the command. `R1_POLICY_SCOPE.json` contains
the authored boundary cases. The artifact records a dirty source snapshot with
implementation hashes; that is disclosed rather than relabeled as a clean run.

## Dominant losses and next interventions

The static-rule allowlist rejects most of this general-question development
stream. Independent checks confirm that benign unsupported technical terms and
fixed system instructions are also excluded. This supports validating a broader
technical scope, not deleting guards or declaring every exclusion unnecessary.
The personal/generative guard contributes a much smaller share of exclusions.

Among eligible requests, lexical scoring rejects most candidates. Next compare
local dense/hybrid retrieval and reranking under independent answer-reuse labels.
Simply lowering the threshold risks incorrect answers. The similarity-only
ablation is not a serving policy. The always-abstaining fixture verifier is not
a live verifier result. Its extra admissions alter future candidate pools, so
its margin/rejection counts are not interchangeable with the similarity run.

## Coverage and limitations

All development requests have terminal outcomes and eligibility reasons;
semantic runs additionally record expiry/eviction counts and candidate/scoring
or verification terminal stages. Provider attempt totals reconcile with the
existing strict answer report. Historical traces lacking instrumentation stay
explicitly unrecorded. Exact-cache expiry/eviction/invalidation attribution is
not available in this trace schema and is not inferred from misses. No such
cause is claimed here. Admission counts overlap rejected-response counts;
terminal outcomes, not all diagnostic counters together, form the partition.

An earlier identical request is not necessarily an available, fresh, correct
cached answer. Candidate recall, safe opportunity coverage and precision remain
unknown without review. Pair labels are never substituted for answer gold.
Fixture timings/tokens do not establish live cost or latency gains.

## Failures, revisions and unresolved risks

The first diagnostic reproduction used an overly broad field named
`retrieval_failure`; it was renamed to `processing_failure` before final
reproduction because malformed verifier contracts can also reach that path.
That run was retained locally and not used for final published artifact hashes.
No inference failures or sealed deviations were hidden. The newly revealed
scope bottleneck is still unfixed; R2 establishes a supported workload before
R3 changes eligibility/matching. No favorable precision or hit-rate claim is
made from these diagnostics.

What to check first: ensure source and trace hashes bind, terminal outcomes
reconcile, missing observations remain unknown, and fixture verifier rejections
are never described as live model accuracy.

## Next phase

R2: establish a useful licensed workload and grouped development/calibration
splits. Source/license research may proceed while the final R1 regression runs;
no R2 implementation is bundled into the R1 phase commit. The running local
live pilot and later independent answer reviews remain external dependencies
for live evidence, not for offline development.
